# QuizClash --- Architecture Specification

**Status:** Architecture source of truth\
**Timebox:** 2--3 days\
**Method:** Spec-Driven Development

## 1. Purpose

This document locks the technology choices, deployment path, system
boundaries, data ownership, and core flows for QuizClash.

Claude Code must not silently change these decisions. If implementation
conflicts with this file, stop and report the conflict before changing
architecture.

## 2. Locked technology stack

-   TypeScript, strict mode
-   React
-   Next.js App Router
-   React Server Components by default
-   Client Components only for browser interactivity
-   Next.js Server Actions for form-style mutations where appropriate
-   Zod shared validation
-   Cloudflare Workers runtime
-   Wrangler
-   **vinext** as the Next.js → Cloudflare Workers deployment path
-   D1 + Drizzle ORM + migrations
-   Durable Objects
-   KV
-   Workers AI
-   Vectorize
-   Queues
-   Vitest

## 3. Locked Next.js + Cloudflare deployment architecture

QuizClash is a **full-stack Next.js application deployed to Cloudflare
Workers**, not Cloudflare Pages.

For a new Next.js project, use Cloudflare's current recommended Workers
path: **vinext**.

Do not use OpenNext unless a verified vinext compatibility gap blocks a
required feature and the architecture is explicitly changed first.

Do not deploy this application as a static Pages export because the
project requires Server Components/Actions and Cloudflare bindings.

### Preferred clean-project bootstrap

For a new repository, prefer Cloudflare C3:

``` bash
npm create cloudflare@latest -- quizclash --framework=next
```

The generated project should already be configured for Next.js +
vinext + Cloudflare Workers.

### Alternative for an existing plain Next.js repository

Before changing anything:

``` bash
npx vinext check
```

Then either initialize vinext directly:

``` bash
npx vinext init
```

and choose Cloudflare Workers, or allow current Wrangler automatic
configuration:

``` bash
npx wrangler setup --dry-run
npx wrangler setup
```

Wrangler automatic Next.js configuration uses vinext.

### Wrangler version

Use a current Wrangler 4.x release. Automatic framework configuration
requires Wrangler \>= 4.68.0.

Check:

``` bash
npx wrangler --version
```

Do not pin an obsolete Wrangler version merely because an old tutorial
uses it.

## 4. Wrangler is infrastructure configuration

The generated `wrangler.jsonc` is the Worker configuration source of
truth for Cloudflare resources and bindings.

Keep it in Git.

Do not commit secrets.

Expected logical bindings:

``` text
DB          -> D1
CACHE       -> KV
AI          -> Workers AI
VECTORIZE   -> Vectorize
GAME_ROOMS  -> Durable Object namespace
POST_GAME   -> Queue
```

Exact resource IDs and generated configuration must follow current
Wrangler/vinext conventions.

After adding/changing bindings, generate TypeScript binding types:

``` bash
npx wrangler types
```

Application server-side code may access Cloudflare bindings using the
supported vinext/Workers mechanism, including `cloudflare:workers` where
appropriate.

Do not wrap every Cloudflare binding in an invented HTTP microservice.

## 5. Development/build/deployment workflow

When scaffolded through C3, prefer the generated package scripts rather
than replacing them.

Conceptual workflow:

``` bash
npm run dev
npm run build
npm run deploy
```

For an existing project migrated with `vinext init`, vinext may provide
explicit scripts such as:

``` bash
npm run dev:vinext
npm run build:vinext
npx @vinext/cloudflare deploy
```

Use the scripts generated by the current toolchain.

For Wrangler-driven configuration/deployment:

``` bash
npx wrangler setup --dry-run
npx wrangler setup
npx wrangler deploy
```

Do not hand-write an obsolete adapter setup when the current generated
configuration already provides the correct integration.

## 6. Runtime model

Production server execution happens in Cloudflare's Workers runtime
(`workerd`), not a traditional long-lived Node.js server.

Before adding dependencies, check for: - Node-only built-ins; -
filesystem assumptions; - native binaries; - unsupported
networking/runtime APIs; - long-lived process assumptions.

Prefer Web Platform APIs and Workers-compatible packages.

Do not change deployment to Node merely because a chosen package is
incompatible.

## 8. Product boundary

-   2--6 players
-   host creates room and chooses topic
-   players join by room code + nickname
-   exactly 5 questions
-   exactly 4 distinct answers per question
-   one represented correct answer
-   one answer per player/question
-   correct = 1 point
-   wrong/timeout = 0
-   final ranking after question 5

Out of scope: authentication, profiles, friends, chat, matchmaking,
uploads, admin UI, tournaments, achievements, complex scoring.

## 9. Data ownership

  Data                         Authoritative owner
  ---------------------------- ---------------------
  Quiz metadata                D1
  Questions / correct answer   D1
  Completed game               D1
  Final player results         D1
  Active room status           Durable Object
  Active players               Durable Object
  Current question             Durable Object
  Submitted answers            Durable Object
  Current scores               Durable Object
  Idempotency records          Durable Object
  Leaderboard snapshot         KV
  Question embeddings          Vectorize
  Post-game event              Queue

KV must remain disposable/rebuildable.

## 10. Routes and component boundaries

Logical routes:

``` text
/                 Landing
/create           Create game
/join             Join game
/room/[code]      Lobby
/game/[code]      Active game
/results/[code]   Results
```

Use Server Components by default for initial rendering/durable reads.

Use Client Components only for genuine browser interactivity such as
answer selection, live game state, and timer presentation.

Do not add `use client` broadly for convenience.

## 11. Question contract

``` ts
type Question = {
  text: string;
  answers: [string, string, string, string];
  correctAnswerIndex: 0 | 1 | 2 | 3;
};
```

A quiz contains exactly five questions.

Zod must reject: - wrong question count; - wrong answer count; - empty
text; - duplicate answers in a question; - correct index outside 0--3.

## 12. AI generation pipeline

``` text
topic
  -> server-side Zod input
  -> Workers AI
  -> parse structured output
  -> shared Zod Quiz schema
  -> Vectorize near-duplicate query
  -> persist accepted quiz to D1
```

Never persist raw AI output before validation.

Zod proves structure, not factual truth. Vectorize detects similarity,
not factual truth. Factual AI errors are an explicit MVP limitation.

## 13. Durable Object invariants

One Durable Object instance represents one room and must enforce:

1.  max 6 players;
2.  game starts once;
3.  only host starts;
4.  joins only while allowed;
5.  player answers current question once;
6.  wrong-question submissions are rejected;
7.  score increments at most once per player/question;
8.  browser never submits authoritative score/correctness;
9.  server compares answer against stored quiz;
10. game progression is authoritative server-side;
11. game finishes once;
12. completed result persists to D1.

## 14. Answer submission

``` text
playerId + questionIndex + answerIndex + idempotencyKey
                         |
                         v
                 Room Durable Object
                         |
             validate player/state/question
                         |
                check idempotency
                         |
                check prior answer
                         |
              evaluate server-side
                         |
                update score once
                         |
             cache idempotent result
```

A retry must never double-score.

## 15. Main flows

### Create game

``` text
nickname + topic
 -> Server Action
 -> Zod
 -> Workers AI
 -> Zod generated quiz
 -> Vectorize duplicate check
 -> D1 persist quiz
 -> initialize room Durable Object
 -> return room code
```

### Join

``` text
nickname + room code
 -> validation
 -> room Durable Object
 -> validate status/capacity
 -> add player
```

### Finish

``` text
question 5 complete
 -> Durable Object calculates ranking
 -> persist completed game/results to D1
 -> mark FINISHED
 -> enqueue post-game event
 -> show results
```

D1 persistence is critical. Queue processing is not.

## 16. D1 model direction

Minimal conceptual schema:

``` text
quizzes(id, topic, created_at, generated_by)

questions(
  id, quiz_id, position, text,
  answer_0, answer_1, answer_2, answer_3,
  correct_answer_index
)

completed_games(id, room_code, quiz_id, started_at, finished_at)

game_results(id, game_id, nickname, score, rank)
```

Refinement is allowed; moving active-room coordination into D1 is not.

## 17. Failure rules

-   Workers AI unavailable before creation -\> clear error; no partial
    game.
-   AI is not required after a game starts.
-   D1 failure while finalizing -\> do not claim durable completion.
-   KV failure -\> core game remains correct.
-   Queue failure/retry -\> completed D1 result remains valid.
-   Client disconnect -\> use a simple MVP timeout/progression rule; no
    complex reconnect protocol unless required.

## 18. Security/trust

Never trust client-provided score, correctness, host privilege, current
question, game status, or final ranking.

Secrets use Cloudflare secret management and are never committed.

Optional protection phase prioritizes: 1. meaningful rate limit; 2.
structured audit logs; 3. safe secrets.

## 19. Tests

Minimum valuable tests:

-   valid/invalid 5x4 Zod quiz contract;
-   duplicate answers rejected;
-   player answers once;
-   idempotent retry does not double-score;
-   wrong question rejected;
-   correct answer scores once;
-   game starts/finishes once;
-   malformed AI output rejected.

## 20. Architecture rules Claude must not violate

Claude Code must not silently: - switch from Workers/vinext to Pages,
Vercel, Node server, or OpenNext; - replace D1/Drizzle; - use KV as
primary storage; - coordinate active games through D1 polling; -
calculate authoritative scores in the browser; - trust AI without Zod; -
claim Vectorize verifies facts; - add authentication, R2, Cron, Redis,
another DB, microservices, or event sourcing.

If current Cloudflare tooling produces a materially different
configuration from this document, first verify current Cloudflare
documentation and report the mismatch rather than forcing stale
configuration.
